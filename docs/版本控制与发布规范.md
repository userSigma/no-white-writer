# 版本控制与发布规范

本规范将「简化版 Git Flow」与项目已落地的 GitHub Actions CI/CD 整合为一份可执行的流程文档。
适用于 no-white-writer 仓库（<https://github.com/userSigma/no-white-writer>）。

> **单人开发适配**：本项目当前为单人开发，涉及"审查人数 / 审查超时"的团队规则以 *单人模式* 标注执行方式；
> 协作者加入后按对应 *团队模式* 条目切换，其余规则不变。

**核心总则：`main` 只接受来自 `develop` 的 Pull Request；唯一例外是 `hotfix/*`**（自 `main` 拉出、修复后直接合回 `main` 即时发布，见 §6.2）。
其余改动——功能、版本号、CI 配置、文档——一律先进入 `develop`，再经 `develop → main` 合入发布。

---

## 1. 分支体系

| 分支 | 类型 | 生命周期 | 用途 |
|---|---|---|---|
| `main` | 发布主线 | 永久 | 仅存放经过验证、可发布的代码；每次合并代表一个可发布版本 |
| `develop` | 开发主线 | 永久 | 唯一的集成分支：一切常规改动的入口，验证达标后合入 `main` |
| `feature/*` | 功能支线 | 临时 | 从 `develop` 分出，单个模块/功能的实现与修复，可并行；也承载 hotfix 补丁回流 |
| `hotfix/*` | 热修复支线 | 临时 | **从 `main` 分出**：修复后直接合回 `main` 发布，同时并入在途 `feature` 线随行进入 `develop` |
| `chore/*` | 辅助支线 | 临时 | 版本号、CI 配置、文档等非功能代码改动，从 `develop` 分出并 PR 回 `develop` |

## 2. 分支操作规则

### main

- 唯一生产可发布分支，**禁止直接 push**（分支保护已开启，直接 push 被远端拒绝）。
- 仅接收来自 `develop` 的 PR；**唯一例外 `hotfix/*`**——自 `main` 分出、修复验证后直接 PR 回 `main` 即时发布（§6.2）。`chore` 等其余分支仍必须先入 `develop`。
- 每次发布合并完成后，立即在合并节点打语义化版本标签 `vX.Y.Z` 并推送远程。
- 标签对应 `pubspec.yaml` 版本号：`version: X.Y.Z+N` → 标签 `vX.Y.Z`（不含 `+N` 构建号）。

### develop

- 常规改动的集成分支：接收 `feature`、`chore` 的 PR；禁止直接 push（分支保护已开启）。
- `hotfix` 补丁经在途 `feature` 线带入（§6.2）；无在途 feature 时可直接 PR 入 `develop` 兜底。
- 功能积累至发布标准、CI 全绿后，发起 PR 合入 `main`。
- 每次 `develop → main` 发布合并后，如需拓扑同源可发 `main → develop` 同步 PR（内容已一致，仅同步合并节点；日常可省略，下次发布前同步即可）。

### feature

- 从**最新的 `develop`** 创建；开发过程中定期同步 `develop`，避免合并冲突。
- 开发完成、本地门禁（见 §5.1）自测通过后，发起 PR 合入 `develop`。
- 在途期间接收 hotfix 补丁合并（§6.2 第 5 步），使修复随 feature 常规 PR 进入 `develop`。
- 合并后立即删除本地与远程的 feature 分支。

### hotfix

- 针对生产环境紧急 bug，**从最新的 `main`（或其发布标签）创建**，确保修复基线与生产一致。
- 修复 + 修订号提升（`pubspec.yaml` 修订号 +1）后，**直接 PR 合入 `main`**——"main 只收 develop PR"总则的唯一例外。
- 合并后在 `main` 合并节点打标签 `vX.Y.(Z+1)` 并推送，Release 工作流自动出包，即为当前版本的 hotfix 发布。
- **补丁同步回开发线**：将 hotfix 分支合并进当前在途的 `feature/*`，随该 feature 的常规 PR 进入 `develop`；无在途 feature 时直接 PR 合入 `develop` 兜底。
- 冲突单人模式下自行解决；双向合并完成后删除 hotfix 临时分支。

### chore

- 版本号提升、CI 工作流调整、文档修正等：从 `develop` 分出，PR 回 `develop`，随 `develop → main` 进入 `main`。

## 3. 分支命名规范

| 类型 | 格式 | 示例 |
|---|---|---|
| 版本标签 | `v主.次.修订`（语义化） | `v0.4.1`、`v1.0.0` |
| 功能 | `feature/模块-内容` | `feature/导出-新增卷级导出` |
| 热修复 | `hotfix/问题-修复` | `hotfix/保存失败-紧急修复` |
| 辅助 | `chore/事项` | `chore/version-0.4.2`、`docs/spec` |

语义化版本号含义：**主版本**＝核心架构/重大变更、不兼容旧版；**次版本**＝新增功能/模块优化、兼容主版本；**修订号**＝bug 修复与小优化、无功能新增。

## 4. PR 管理规范

### 4.1 描述模板（四项核心内容，缺一不可）

```markdown
## 修改目的
（开发/修复的原因；有需求编号/BUG 单号一并附上）

## 核心逻辑
（实现思路与关键修改点）

## 测试方式
（测试方法、用例与结果；至少写明 flutter test 通过数）

## 模块影响
（对其他模块的影响、是否需要联动、兼容性问题）
```

### 4.2 审查与合入规则

| 流向 | 单人模式 | 团队模式（未来切换） |
|---|---|---|
| `feature/chore → develop` | CI 绿灯 + 按 §4.1 模板自查 | 至少 1 名成员审查 |
| `hotfix → main`（总则唯一例外） | CI 绿灯 + 自查，尽快完成 | 1 名核心开发/负责人优先快速审查 |
| `hotfix → feature/*`（补丁回流） | 随 feature 常规 PR 一并审查 | 同左 |
| `develop → main` | CI 绿灯 + 本地全量门禁通过 | 至少 2 名核心成员审查 + 全量验证 |

- **CI 是硬门禁**：PR 触发的 `CI` 工作流（格式/分析/测试/Windows 构建）不通过不得合入。
- 合并方式：默认 `merge`（保留分支拓扑，与既有历史一致）；合入后及时删除临时分支。
- PR 驳回：标注原因与修改意见，发起人修改后重新提交。超时（3 个工作日未审）：单人模式自查滞留原因；团队模式由发起人提醒审查者。

## 5. CI/CD 执行规则

### 5.1 本地门禁（push / 发 PR 前必过）

```powershell
flutter pub get
dart format --output=none --set-exit-if-changed .   # 格式 0 变化
flutter analyze                                     # 无问题
flutter test                                        # 全部通过
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tool/fix_plugin_symlinks.ps1  # 仅本机需要
flutter build windows --release                     # 发布前验证编译
```

- `tool/fix_plugin_symlinks.ps1` 是本机无开发者模式时的 junction 补丁，**CI 托管 runner 不需要**，勿写进工作流。
- CI 的 Flutter 版本锁定在 `FLUTTER_VERSION: 3.47.7`（与本地一致）；升级 SDK 需先本地全量验证再改两个工作流。

### 5.2 CI 自动验证（`.github/workflows/ci.yml`）

触发：push 到 `main`/`develop` + 所有 PR；同分支并发自动取消旧跑。

| Job | 运行环境 | 内容 |
|---|---|---|
| quality（格式/分析/测试） | ubuntu-latest | `pub get` → `dart format` 0 变化 → `analyze` → `test` |
| windows-build | windows-latest | `pub get` → `build windows --release` → 产物存 7 天备查 |

依赖按已提交的 `pubspec.lock` 安装，保证与本地一致。

### 5.3 CD 发布（`.github/workflows/release.yml`）

触发：推送 `v*` 标签。对应"半手动 CD"：**人决定何时打标签，出包全自动**。

流程：`pub get` → `analyze` → `test` → 标签/`pubspec` 版本一致性校验 → Windows x64 release 构建 → ZIP + SHA-256 → 创建 GitHub Release（自动生成发布说明）。

产物命名：`no-white-writer-<版本>-windows-x64.zip`（+ 同名 `.sha256`）。

## 6. 发布流程

### 6.1 常规发布（develop → main）

1. 功能经 `feature/*` PR 合入 `develop`，CI 绿灯、本地全量门禁通过；
2. `chore/version-X.Y.Z` PR 提升 `pubspec.yaml` 版本号（`version: X.Y.Z+N`），合入 `develop`；
3. 发起 `develop → main` 的发布 PR，审查合入；
4. 在 `main` 合并节点打标签并推送：`git tag vX.Y.Z && git push origin vX.Y.Z`；
5. Release 工作流自动构建并发布 ZIP + SHA-256；
6. 核对 [Releases](https://github.com/userSigma/no-white-writer/releases) 资产，把 SHA-256 补进 `README.md` 发布记录段（改动同样先入 `develop`，随下次发布或立即同步进 `main`）；
7. `develop` 已含全部发布内容，直接作为下一轮开发基线；如需与 `main` 拓扑同源，补一个 `main → develop` 同步 PR。

### 6.2 hotfix 发布（main → main，总则唯一例外）

1. 从最新 `main`（或对应发布标签）创建 `hotfix/问题-修复` 分支；
2. 修复 bug，并将 `pubspec.yaml` 修订号 +1（如 `0.4.1+5 → 0.4.2+6`）；
3. PR 合入 `main`（唯一例外通道），CI 绿灯后合并；
4. 合并节点打标签并推送：`git tag vX.Y.(Z+1) && git push origin vX.Y.(Z+1)`，Release 工作流自动发布 hotfix 版 ZIP + SHA-256；
5. **补丁回流开发线**：将 hotfix 分支合并进在途 `feature/*`（无在途 feature 时直接 PR 入 `develop` 兜底）；
6. 删除本地与远程 hotfix 分支。

> 注意：`release.yml` 必须存在于打标签的那个提交里。
> 非 `v*` 开头的标签（如 `alpha`）不会触发发布。

## 7. 特殊场景

### feature 开发中断/废弃

评估是否保留：不保留 → 删除远程与本地分支；需保留 → 重命名为 `feature/模块-开发中断-备注` 并在描述中注明状态。

### 多版本并行维护

当前单产品线阶段**不启用**；hotfix 直入 `main` 的例外已由 §6.2 确立，若未来需为旧生产版本独立修复，基于该通道扩展（从旧标签切 hotfix，合入 `main` 打新修订号标签），届时修订本规范后执行。

### 回退

桌面应用无服务端回滚概念：生产问题走 hotfix 出新修订版；需要旧版时直接从 Releases 页取历史 ZIP（均有 SHA-256 校验）。

## 8. 分支保护落地清单

- [x] `main`：禁止直接 push / 强推 / 删除（2026-10-28 实测：直接 push 被拒）；ruleset 不限制 PR 源分支，`hotfix/* → main` 例外通道可用
- [x] `develop`：禁止直接 push / 强推 / 删除（2026-10-28 实测：直接 push 被拒）
- 远程仅允许删除 `feature`/`hotfix`/`chore` 临时分支。
